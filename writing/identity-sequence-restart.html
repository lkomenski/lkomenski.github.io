The IDENTITY sequence restart that orphaned my ChartEntry rows — and why I chose delete-and-reinsert over a patch

SQL Server · Star Schema Migration · Data Integrity · 8 min read · Hidden Gem Music Capstone

From the project

Hidden Gem Music

Cross-regional music discovery platform · 28M rows · SQL Server · .NET 9

View Project →

The star schema migration was going well. The DDL had run cleanly, the new dimension tables were in place, and the ingestion scripts had been rewritten to target DIM_Song, DIM_Artist, and Bridge_SongArtist instead of the old 3NF tables. Then I ran the verification checks and the numbers were wrong. Not slightly wrong — wrong in a way that meant something had gone badly off somewhere in the migration.

The root cause took a while to find. What looked like a data problem turned out to be a sequence problem — and understanding why led to a fix decision that was as much about code quality as it was about getting the numbers right.

What happened

The star schema migration replaced five 3NF tables — Song, Artist, ArtistSong, AudioFeatures, and Album — with three dimensional tables: DIM_Song, DIM_Artist, and Bridge_SongArtist.

The migration process dropped the old tables and created the new ones, then ran the rewritten ingestion scripts to repopulate them. FACT_ChartEntry was untouched throughout — all 28 million rows stayed in place, with their existing song_id values intact. The plan was that DIM_Song would be populated with the same song_id values the original Song table had, so FACT_ChartEntry's foreign keys would still resolve correctly.

The problem: when DIM_Song was created as a new table, its IDENTITY sequence started at 1 and incremented from there. Dataset 1 was ingested first — those songs got song_id values starting from 1, which happened to match what FACT_ChartEntry was already pointing at for DS1 rows. Everything looked fine for DS1.

Dataset 2 was ingested second. But the songs that appeared in DS2 and not DS1 got new song_id values assigned by the fresh IDENTITY sequence — values that were different from what the DS2 rows in FACT_ChartEntry had been pointing at before the migration. Those DS2 FACT_ChartEntry rows now had song_id values that didn't exist anywhere in DIM_Song. They were orphaned.

What orphaned rows look like

A LEFT JOIN from FACT_ChartEntry to DIM_Song on song_id returns NULL for all song columns on the affected rows. The chart entry exists. The song it references does not. Queries that filter for non-NULL song data silently exclude those rows — no error, just wrong counts.

Why the root cause wasn't obvious immediately

When verification checks came back wrong, the first assumption wasn't the IDENTITY sequence — it was the ingestion scripts themselves. Were rows being dropped during the deduplication logic? Was the spotify_id parsing producing different results the second time? Was a column constraint silently rejecting rows?

Working through those possibilities took time. The DS1 numbers looked correct, which narrowed it to something specific to the DS2 ingestion or the DS2 rows in FACT_ChartEntry. Querying the orphaned rows directly is what finally made it clear: 

-- Find ChartEntry rows with no matching DIM_Song entry
SELECT COUNT(*)
FROM FACT_ChartEntry ce
LEFT JOIN DIM_Song ds ON ce.song_id = ds.song_id
WHERE ds.song_id IS NULL
  AND ce.source = 'Dataset2';

The count came back non-zero. That's when the IDENTITY sequence became the obvious explanation — DS2 songs that weren't in DS1 had been assigned new IDs that didn't match what FACT_ChartEntry was already holding.

Two options, one decision

Once the root cause was clear, there were two ways to fix it.

Option 1: Update. Query DIM_Song to find the new song_id for each affected song, then UPDATE the corresponding FACT_ChartEntry rows to point at the correct new ID. Technically possible. But it required matching songs across the old and new ID spaces — using spotify_id as the bridge — and updating 2 million rows in the fact table. Doable, but complex, and any error in the matching logic would produce quietly wrong data that was hard to verify.

Option 2: Delete and reinsert. Delete the DS2 rows from FACT_ChartEntry and rerun the DS2 ingestion script, which would now correctly resolve song_id values against the populated DIM_Song table. The DS2 ingestion script already existed and had already run successfully once. Running it again — after truncating the DS2 FACT_ChartEntry rows — was straightforward.

I chose delete-and-reinsert. Not because it was easier in the moment — it meant reingesting 2 million rows — but because it was cleaner in every way that mattered.

Why clean mattered more than fast

The update approach would have fixed the numbers. But it would have introduced a one-off correction — a patch applied on top of an ingestion that had gone wrong — that would live in the documented history of the project alongside code that assumed the ingestion was correct.

I didn't want that. The ingestion scripts are documented. They're in the repo. They're the record of how the data got into the database. If those scripts produce the wrong result when run in sequence, that's a problem with the scripts — not something to paper over with a correction script run afterward.

More practically: I wanted the ingestion scripts to be re-runnable from scratch. If someone needed to rebuild the database from the raw data files — whether for a future iteration, a new environment, or a disaster recovery — running the scripts in order should produce a correct result. An update patch applied after the fact doesn't survive that scenario. A correct ingestion script does.

The ChartEntry fix

Delete all DS2 rows from FACT_ChartEntry using the source column tag. Rerun the DS2 ingestion script, which now resolves song_id via a lookup against the populated DIM_Song table rather than assigning new IDENTITY values. Verify row counts. Done. 

-- Remove DS2 ChartEntry rows before reingestion
DELETE FROM FACT_ChartEntry
WHERE source = 'Top50_73_Countries';

-- Verify DS1 rows are untouched
SELECT COUNT(*) FROM FACT_ChartEntry WHERE source = 'Spotify_Historical_Charts';
-- Expected: 26,173,514

-- Then rerun DS2 ingestion script
-- Expected DS2 count after: 2,110,316

The cascade: it didn't stop at ChartEntry

Fixing the ChartEntry orphans wasn't the end of it. The same IDENTITY sequence problem had cascaded into every pre-computed summary table that held a song_id foreign key.

Five summary tables — PeakReachBySong, TrendVelocityBySong, HiddenGems, SongCountryPresence, and DiscoveryGapByDay — had all been populated before the migration. Every row in those tables referenced pre-migration song_id values from the old Song table. After migration, those IDs no longer existed in DIM_Song. Every row in every summary table was orphaned.

The fix for those was simpler than the ChartEntry fix, but it had to happen in the right order. Truncate all summary tables, re-add the foreign keys to the now-empty tables successfully, then rerun all population procedures in full against the correct DIM_Song IDs: 

-- Truncate all summary tables before re-adding FKs
TRUNCATE TABLE SongCountryPresence;
TRUNCATE TABLE DiscoveryGapByDay;
TRUNCATE TABLE PeakReachBySong;
TRUNCATE TABLE TrendVelocityBySong;
TRUNCATE TABLE HiddenGems;
-- (and remaining summary tables)

-- FK re-adds now succeed against empty tables
-- Then run population procedures in dependency order:
EXEC sp_PopulateSongCountryPresence;
EXEC sp_PopulateCountryYearStats;
EXEC sp_PopulateGlobalOverlapByYear;
EXEC sp_PopulateTrendVelocityBySong;
EXEC sp_PopulateDiscoveryGapByDay;
EXEC sp_PopulateIsolationScoreByCountry;
EXEC sp_PopulatePeakReachBySong;
EXEC sp_PopulateHiddenGems;

There was also a double ingestion problem discovered during verification. At some point during the migration, both DS1 and DS2 had been ingested twice — producing roughly 56 million total rows in FACT_ChartEntry instead of 28 million. DS1 appeared under two different source tag values from the two ingestion runs. DS2 appeared twice under the same tag. The targeted delete by source tag resolved DS1. For DS2, where the tag was identical across both runs, the fix used the chart_entry_id midpoint to cleanly split the two insertions: 

-- DS1 duplicate: different source tags, easy to target
DELETE FROM FACT_ChartEntry
WHERE source = 'Historical_Top200_and_Viral50';

-- DS2 duplicate: same source tag, use ID midpoint to identify second insertion
DELETE FROM FACT_ChartEntry
WHERE source = 'Top50_73_Countries'
  AND chart_entry_id > 60616149;

Final verified counts after all fixes: DS1 26,173,514 rows, DS2 2,110,316 rows, combined 28,283,830. Zero orphaned rows. Zero FK violations. All summary tables repopulated correctly.

What to do differently from the start

The immediate lesson is specific to schema migrations in SQL Server: when you drop and recreate a table with an IDENTITY column, the sequence resets. If other tables hold foreign keys to the old IDs, those references are now broken. The fix is to ensure that rows in dependent tables are deleted and reinserted after the migration, not left in place expecting the new table to match the old ID space.

The broader lesson is about ingestion script design. The source column on FACT_ChartEntry — a simple NVARCHAR column hardcoded to 'Dataset1' or 'Dataset2' during ingestion — is what made the targeted delete possible. Without it, separating DS1 and DS2 rows for a partial delete would have required a date range filter or a join back to DIM_Song, both of which are less reliable than a direct tag.

Tagging rows by source at ingestion time costs nothing and makes every subsequent operation that touches one dataset but not the other — reingestion, validation, targeted fixes — significantly simpler. It's the kind of decision that feels like overhead when you make it and like obvious foresight when you need it later.

The re-runnable ingestion script principle is the same category of decision. It feels like extra care in the moment. It's the thing that lets you fix a problem cleanly instead of patching it — and it's the difference between documented work you stand behind and documented work you have to explain around.
