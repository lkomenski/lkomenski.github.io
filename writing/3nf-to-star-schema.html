Why we migrated from 3NF to star schema mid-project — and why it was the right call

SQL Server · 10 min read · Hidden Gem Music Capstone

We started building Hidden Gem Music on a fully normalized 3NF schema. At design time, that made sense — it's what you learn first, it's well-understood, and the principles behind it are sound. What we didn't fully account for was the nature of our actual workload. By the time we were deep into stored procedure development and seeing the impact on load times, it was clear the schema was working against us. This is the story of how we caught it, what the migration involved, and what I'd tell someone earlier in the same project.

The 3NF schema and what it was designed to do

Third Normal Form exists to protect data integrity during writes. It eliminates redundancy, prevents update anomalies, and ensures that changing one piece of data doesn't silently corrupt another. For a transactional database — one where records are created, updated, and deleted regularly — these guarantees matter enormously.

Our original schema reflected those principles. Song data was split across Song, Artist, ArtistSong, AudioFeatures, and Album — each table responsible for exactly one thing, relationships enforced through foreign keys, no redundant data anywhere. Clean, correct, normalized.

The problem was that we weren't building a transactional database. We were building an analytical one.

Three things that told us something was wrong

1. Frontend load times

The first red flag showed up in the frontend. Pages that should have been fast weren't. When you can see the impact of what's happening in the database reflected in browser load times, something is structurally wrong — that's not a query optimization problem, that's an architecture problem. The schema was making the API work too hard to return data the UI needed.

2. The joins

Writing the stored procedures made it obvious. To return a song title and artist name — the most basic piece of display data in the entire app — required joining through Song, ArtistSong, Artist, and depending on the endpoint, Album as well. Four tables for display labels. Every read procedure had that join chain at its core.

I knew there had to be a better way. That instinct was the starting point.

3. The data itself

The third piece was realizing what the data actually was: archival. 28 million rows ingested once from two Kaggle datasets, never updated, never deleted, never written to again after the initial load. Historical Spotify chart data doesn't change. There are no concurrent writes to protect against. There are no update anomalies to prevent because there are no updates.

3NF is solving problems we don't have. And it's creating performance problems we do.

The core realization: 3NF is optimized for write safety. Star schema is optimized for read performance. Our database is written once and read constantly. We were using the wrong tool.

What star schema actually changes

A star schema puts the fact table at the center — in our case, FACT_ChartEntry, which holds every chart entry across every country and date — and surrounds it with flattened dimension tables. Instead of normalizing song data across five tables, everything about a song lives on DIM_Song. Instead of joining through ArtistSong to get artist names, a bridge table Bridge_SongArtist resolves the many-to-many relationship directly.

The practical effect: what used to require a four-table join chain is now a single indexed lookup on an integer primary key. At 28 million rows in FACT_ChartEntry alone, that difference compounds across every stored procedure, every API call, every page load.

Audio features, which we'd previously isolated in a separate AudioFeatures table to signal they were secondary data, moved onto DIM_Song as nullable columns. No extra join needed — they're just there if they exist, null if they don't. Album data did the same: instead of maintaining a surrogate key and a foreign key relationship for a display label, album_name is a plain string column on DIM_Song. No procedure groups by album. It was never a queryable entity — it was always just a label.

What the migration actually involved

I want to be honest here: it wasn't trivial. It wasn't a full rebuild from scratch, but it was a significant amount of work and it required careful sequencing.

The migration involved re-ingesting data into the new dimensional tables, rethinking the overall design to make sure everything mapped correctly, rewriting all seven read stored procedures that touched song or artist data, and repopulating all the pre-computed summary tables that feed the API at runtime. There was also refinement work afterward — the first pass wasn't perfectly optimized and loading performance needed tuning once the new schema was in place.

One specific issue worth calling out: the IDENTITY sequence restart after migration caused orphaned rows. The fix required a full delete-and-reinsert of the affected rows rather than an update — another reminder that in a write-once analytical database, the ingestion layer has to be designed to be re-runnable.

The eight population stored procedures — the expensive ones that run against FACT_ChartEntry directly and pre-compute the summary tables — required no changes at all. They operate on the fact table and summary tables, neither of which changed. That was a relief.

What the schema looks like now

FACT_ChartEntry          -- 28M rows. Center of the schema.
  song_id   → DIM_Song
  country_id → Country
  chart_type_id → ChartType
  snapshot_date, rank, streams, popularity...

DIM_Song                 -- One row per unique track.
  song_id, spotify_id, title
  album_name, album_release_date  -- plain strings, no FK
  danceability, energy, valence... -- audio features, nullable

DIM_Artist               -- One row per unique artist.
  artist_id, artist_name

Bridge_SongArtist        -- Many-to-many resolution.
  song_id, artist_id, artist_order

Six read procedures required no changes because they query only pre-computed summary tables — no song or artist dimension data needed. The seven that did change all followed the same pattern: replace the multi-table join chain with the star schema equivalents, read album_name directly from DIM_Song as a string.

What I'd tell someone earlier in the same project

Think about what the future of your data actually is before you design your schema — not just what the data is, but what will be done with it and whether it will ever change.

The question that unlocks the right decision is simple: is this database transactional or analytical? If records are being created, updated, and deleted regularly, 3NF's write protections are genuinely valuable. If data is written once and read constantly — especially at scale — 3NF is adding join overhead with no corresponding benefit.

We didn't need a transactional database because we were never going to update the data. We needed to store 28 million rows as efficiently as possible and get aggregated results to the user as quickly as possible. Star schema is built for exactly that workload.

There's also a forward-looking argument: star schema makes future data expansion significantly easier. If we were to backfill data — add new countries, extend the date range, bring in a third dataset — the dimensional model accommodates that more cleanly than a normalized schema would. New rows in the fact table, new or updated dimension rows, repopulate the summary tables. The architecture doesn't fight you.

The migration cost us time. But the alternative — shipping a product with the wrong schema baked in and performance problems that couldn't be tuned away — would have cost more. Sometimes the right call is the harder one.
