Why the API never touches the fact table: designing for a 28M-row read workload

SQL Server · Architecture · Pre-Computation · 10 min read · Hidden Gem Music Capstone

From the project

Hidden Gem Music

Cross-regional music discovery platform · 28M rows · SQL Server · .NET 9

View Project →

The central fact table in the Hidden Gem Music database holds 28 million rows — every chart entry, across every country, across every date in both datasets. The application needs to answer questions like: which songs appear in multiple countries? How long does it take a song to cross a border? Which country is most isolated from global trends?

Answering those questions by querying 28 million rows at runtime was never a realistic option. The realization wasn't gradual — looking at the scale of the data made it immediately obvious that no machine was going to sift through that at request time, and that even with indexes and optimized joins, the math didn't work. The application would be unusable.

The solution is pre-computation: a set of summary tables that are built once by expensive population procedures, and then queried cheaply at runtime by fast read procedures. The API never touches FACT_ChartEntry directly. Every endpoint reads from a pre-computed result. This post is about why that architecture exists, how it's structured, and what the dependency chain between the summary tables actually means in practice.

The two classes of stored procedure

The database has two fundamentally different kinds of stored procedure, and keeping them distinct is the foundation of the whole architecture.

Population procedures are expensive. They run against FACT_ChartEntry directly, doing full aggregations across millions of rows, computing cross-country comparisons, calculating date differences, ranking songs by presence count. They run once — on data load, or when something in the underlying data changes. They are never called at request time. Ever.

Read procedures are cheap. They query only pre-computed summary tables, which are small, indexed, and already contain the answer. These are what the API calls. A typical read procedure is a handful of SELECT statements against tables with thousands of rows, not millions. Response times are fast because the work was already done.

The core principle

Anything the application needs to display that requires aggregation, cross-country comparison, or calculation across the full dataset must be pre-computed and stored — not derived at request time. The raw data answers the question once. The summary table holds that answer for every subsequent request.

What each summary table holds

Table What it stores What it feeds
SongCountryPresence For each song and year: how many distinct countries it charted in Hidden Gems logic, overlap calculations
SongCountryChart Which songs charted in which countries, deduplicated per year Country comparison, overlap percentage
DiscoveryGapByDay For each song: origin country and days to each subsequent country KPI 2 (Discovery Gap), gap distribution histogram
PeakReachBySong Highest simultaneous country count per song, with date KPI 4 (Peak Cross-Regional Reach)
GlobalOverlapByYear Year-by-year overlap rate and average countries per song Dashboard trend line, KPI 1
CountryYearStats Per country per year: total charted, shared, unique, overlap % Country profile, comparison page, KPI 1
IsolationScoreByCountry Per country: isolation score %, isolation tier KPI 3 (Most Isolated Region), isolation bar chart
HiddenGems Songs charting in N+ countries but absent from a given country Hidden Gems screen, country page preview
TopSongByCountryYear One representative top song per country per year Globe card display

Each of these tables represents one pre-answered question. The read procedures don't compute — they retrieve.

The dependency chain — and how it emerged

The population procedures have to run in a specific order. Some summary tables depend on other summary tables being populated first — they don't query FACT_ChartEntry directly, they query an already-computed result. Run them out of order and you get empty joins, wrong counts, or silent data gaps with no error to tell you what happened.

This dependency chain wasn't designed upfront. It emerged as the population procedures were built, when it became clear that certain calculations required intermediate results that only existed in another summary table. DiscoveryGapByDay needs song-country presence data. GlobalOverlapByYear needs presence counts. IsolationScoreByCountry needs country-year statistics. Once that structure became visible, the order had to be documented and enforced — because nothing in SQL Server enforces it for you.

1. sp_PopulateSongCountryPresence → feeds everything downstream
2. sp_PopulateSongCountryChart → feeds comparison and overlap logic
3. sp_PopulateDiscoveryGapByDay → depends on SongCountryPresence
4. sp_PopulatePeakReachBySong → depends on SongCountryPresence
5. sp_PopulateGlobalOverlapByYear → depends on SongCountryPresence
6. sp_PopulateCountryYearStats → depends on SongCountryChart
7. sp_PopulateIsolationScoreByCountry → depends on CountryYearStats
8. sp_PopulateTrendVelocityBySong
9. sp_PopulateHiddenGems → depends on SongCountryPresence + SongCountryChart
10. sp_PopulateTopSongByCountryYear → lightweight globe display data
11. sp_PopulateTopSongByCountryYear (final pass)

SongCountryPresence is the foundation. It counts how many distinct countries each song charted in per year, with Viral 50 entries excluded. Almost everything downstream depends on that count existing first. If you truncate SongCountryPresence and don't repopulate it before running sp_PopulateHiddenGems, the Hidden Gems table populates with zero rows and no error is thrown. The data is just wrong.

What breaks if you run out of order

SQL Server will not warn you that a dependency table is empty. Population procedures will complete successfully with zero rows written to the target table if the upstream table they depend on hasn't been populated. The verification step after every repopulation run isn't optional — it's the only thing that catches a dependency violation.

What the read procedures actually do

Once the summary tables are populated, the read procedures are straightforward. Here's the difference in practice:

A naive "what's the global overlap rate?" query against the raw data would look something like this — a full aggregation across the fact table: 

-- What you do NOT want at runtime
SELECT
    COUNT(DISTINCT song_id) AS total_songs,
    COUNT(DISTINCT CASE WHEN country_count >= 2
        THEN song_id END) AS songs_in_2plus_countries
FROM (
    SELECT song_id, COUNT(DISTINCT country_id) AS country_count
    FROM FACT_ChartEntry
    WHERE chart_type_id != 2
    GROUP BY song_id, YEAR(snapshot_date)
) sub;

That query scans 28 million rows, does a full aggregation, and returns one number. At runtime, on a user request, that's not acceptable.

The actual read procedure queries GlobalOverlapByYear, which already has the answer: 

-- What actually runs at request time
SELECT
    overlap_pct,
    total_unique_songs,
    songs_in_2plus_countries
FROM GlobalOverlapByYear
WHERE chart_year BETWEEN @YearStart AND @YearEnd;

Same answer. Milliseconds instead of seconds. The work happened once, at population time. Every subsequent request just reads the result.

The tradeoff you're accepting

Pre-computation trades freshness for speed. The summary tables reflect the state of the data at the last time the population procedures ran. If something changes in FACT_ChartEntry — a fix, a re-ingestion, an exclusion rule update — the summary tables are stale until you repopulate.

For Hidden Gem Music, this tradeoff costs nothing. The data is historical and archival — it doesn't change after ingestion. The population procedures ran once when the data was loaded, and the summary tables have been correct since then. There is no freshness concern because there is no new data arriving.

In a production system with live data, this would be a real architectural consideration: how often do you repopulate, what triggers it, what do users see during a repopulation run? For a write-once analytical database, those questions don't apply — which is part of why this architecture is such a clean fit for this workload.

The principle underneath it

The pre-computation architecture is a specific application of a broader principle: match your data architecture to your actual workload, not to the workload you might have.

A transactional database with live writes needs a different architecture than an analytical database with a fixed historical dataset. A system that needs real-time aggregations needs a different architecture than one where the aggregations never change. The mistake is applying a general pattern without asking whether the pattern fits the specific constraints you're working under.

For this project: 28 million rows, written once, read constantly, no updates ever. The answer was obvious once the problem was stated clearly. The implementation — eleven population procedures, a strict dependency chain, summary tables that give the API pre-answered questions — followed from that.

The dependency chain wasn't planned. It emerged as each population procedure was written and revealed what it needed from upstream. That's fine — recognizing the dependency structure and documenting it correctly is what matters, not whether you saw it coming. Architecture doesn't always arrive fully formed. Sometimes you build it and then you see what it is.
