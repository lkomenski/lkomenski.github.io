Two datasets that can't be directly compared — and how we handled it

SQL Server · Schema Design · Data Integrity · 9 min read · Hidden Gem Music Capstone

From the project

Hidden Gem Music

Cross-regional music discovery platform · 28M rows · SQL Server · .NET 9

View Project →

Hidden Gem Music is built on two Kaggle datasets that cover overlapping subject matter — Spotify chart data across dozens of countries — but differ in almost every structural detail. Different country formats, different song identifiers, different chart types, different date ranges, and crucially: different ways of measuring popularity.

Most of those differences can be bridged. The popularity metrics cannot. Dataset 1 measures popularity with raw stream counts. Dataset 2 uses Spotify's proprietary 0–100 popularity score. These are not the same thing, they are not convertible to each other, and putting them in the same column or using them in the same calculation produces a number that is analytically meaningless.

This isn't a bug that showed up during testing. It's a constraint that was visible during schema design and had to be built around from the beginning. Here's how we handled it and why the decisions made at the schema level had to be enforced all the way through to the stored procedure layer.

What the two datasets actually measure

Property Dataset 1 (2017–2021) Dataset 2 (2023–2025)
Coverage Top 200 + Viral 50, every 2–3 days Top 50 per country, daily
Country format Full name ("United States") ISO code ("US")
Song identifier Spotify URL (ID parsed from URL) Native Spotify ID
Popularity metric Raw stream count (BIGINT, can be NULL for Viral 50) Proprietary score 0–100 (TINYINT)
Movement data Categorical string (MOVE_UP, MOVE_DOWN, SAME, NEW_ENTRY) Integer deltas (daily_movement, weekly_movement)
Audio features None 13 columns (danceability, energy, valence, tempo, etc.)

The stream count vs. popularity score difference is the most important one. A song with 5 million streams in 2019 cannot be meaningfully compared to a song with a popularity score of 72 in 2024. The first is an absolute count of listening events. The second is a relative, proprietary score that Spotify recalculates continuously based on recent plays, velocity, and other undisclosed factors. The scale, the methodology, and the meaning are all different.

Why you can't convert between them

Stream counts are absolute and historical — they represent something that happened and was measured. Spotify's popularity score is relative and dynamic — it reflects current momentum against all other tracks at a given moment. There is no conversion formula. A song with 10 million streams might have a popularity score of 40 or 90 depending on when you look and what else is popular at that moment.

The schema decision

The decision was made during schema design, before any data was ingested: store both metrics as separate nullable columns on FACT_ChartEntry, never merge them, and enforce that separation in every stored procedure that touches either column. 

-- FACT_ChartEntry — relevant columns
streams     BIGINT   NULL,  -- DS1 Top 200 only. NULL for Viral 50 + all DS2.
popularity  TINYINT  NULL,  -- DS2 only. NULL for all DS1.
                            -- Never used in the same calculation.

This means every row in FACT_ChartEntry has either a stream count or a popularity score — never both, because no row belongs to both datasets. The separation is enforced by the data itself: DS1 rows have streams populated and popularity NULL. DS2 rows have popularity populated and streams NULL.

Storing them separately rather than trying to normalize them into a single column was a deliberate choice. The temptation with incompatible metrics is to find a normalization approach — divide streams by some constant, scale to a 0–100 range, something that produces a single comparable number. That approach produces a number that looks comparable but isn't. The math works. The meaning doesn't.

What goes wrong if you ignore this

Averaging streams and popularity together — or treating a song's popularity score as equivalent to its stream count for ranking purposes — produces output that is internally consistent but analytically wrong. The result would tell you something. It just wouldn't tell you what you thought it was telling you. That's the most dangerous kind of wrong number.

How the separation is enforced in practice

A schema decision only holds if it's respected throughout the codebase. The two columns being separate doesn't prevent a careless stored procedure from joining them. Enforcing the constraint meant making it explicit in every population and read procedure that touches popularity data.

In practice this means a few things:

KPI calculations never mix the two metrics. The Global Overlap Rate, Discovery Gap, and all other dashboard KPIs are calculated from chart presence — which country a song charted in, on which date, at what rank. Rank is comparable across both datasets. Neither streams nor popularity feeds into the core KPI calculations directly.

Any procedure that surfaces popularity data filters by dataset. If a read procedure needs to return something about a song's popularity, it specifies which metric it's using and filters accordingly — either WHERE streams IS NOT NULL for DS1 data or WHERE popularity IS NOT NULL for DS2 data. Never both in the same result set without explicit labeling.

The movement columns have the same constraint. DS1's trend column is a categorical string. DS2's daily_movement and weekly_movement are integer deltas. They measure the same concept — how a song's rank is changing — but in different formats that aren't directly comparable. Both are stored as separate nullable columns. The TrendVelocityBySong pre-computed table normalizes them into a common format at population time so read procedures never have to handle the discrepancy at runtime.

What the project can and can't say about the two periods

Keeping the metrics separate also shapes what the application can honestly claim. The 22-month gap between the two datasets — December 2021 to October 2023 — is documented on the welcome screen and marked visually in every time-series chart. But the incompatibility of the popularity metrics means the limitation goes further than just the gap.

The application can compare chart overlap across both periods — which songs appeared in multiple countries, how many days it took a song to cross borders, which markets are most isolated. Those questions are answered using rank and presence data, which is comparable across datasets.

The application cannot say "songs in 2019 were more popular than songs in 2024" using the available metrics, because the metrics are different. It cannot rank a 2018 song against a 2024 song by popularity. Every visualization that involves popularity data is scoped to one dataset or the other, never both combined.

The principle

Understanding what your data can't tell you is as important as understanding what it can. Building that constraint into the schema — rather than leaving it as a note in a readme that someone might miss — means the application can't accidentally produce a misleading answer even if a future stored procedure is written without that context in mind.

Why this decision belonged at schema design time

The incompatibility between stream counts and popularity scores was visible as soon as the two datasets were examined side by side. One has a streams column. The other has a popularity column. They're different column names, different data types, different scales. The constraint didn't need to be discovered — it was there from the start.

Making the decision at schema design time rather than deferring it meant that every stored procedure written afterward was written with the constraint already in place. No procedure was written assuming the metrics were comparable and then had to be rewritten when that assumption turned out to be wrong.

That's the value of understanding your data before you build with it. Not every constraint can be anticipated — but the ones that are visible at the start should be built around at the start. The alternative is discovering them later, when they've already propagated through the codebase and have to be fixed everywhere at once.
